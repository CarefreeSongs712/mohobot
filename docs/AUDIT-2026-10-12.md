## P1 级问题

### P1-1 LLM 错误文案被当作正常回答写入记忆、数据库和情感分析

**位置**：[llm_service.py:214–248、325–365](<../mohobot/llm_service.py#L214-L365>) 缺 Key、API 异常、空流均返回普通字符串；[message_handler.py:604–639](<../mohobot/message_handler.py#L604-L639>) 只判断 `full_reply.strip()` 非空即回写。

**用户影响**：网关 429、Key 失效、空流时，`[LLM 调用失败: ...]` 或「LLM 服务未配置」被保存为 bot 说过的话，进入后续上下文、压缩总结和情感分析；错误原文还直接发给用户。

**复现**：未配置 Key 时调用真实 `_handle_message` → contexts 中 assistant 为「LLM 服务未配置（缺少 API Key）…」，DB 写入 2 行，消息已发出。

**修复方案**：
- `chat`/`chat_stream` 返回结构化结果（`completed / failed / partial` + 正文 + 诊断），诊断不作为正文。
- 主链只在 `completed` 时回写 contexts/DB/情感；失败时给用户固定简短提示，异常细节仅写日志。
- A/B 路径已用异常表达失败，不需改动，可作为参照。

**验收**：四种 stream/segment 组合 × 缺 Key / 请求异常 / 空流 / 工具续轮失败；断言 contexts、DB、情感均无错误正文，用户提示不含异常详情。

### P1-2 排队中的消息被取消后仍会发送，且不归档、残留追踪

**位置**：[outbound.py:106–141](<../mohobot/services/outbound.py#L106-L141>) worker 不检查调用方是否已取消；[ws_server.py:321–344](<../mohobot/ws_server.py#L321-L344>) 只捕获 `Exception`，`CancelledError` 跳过清理与归档。

**用户影响**：A/B 评估的 15 秒发送超时、插件重载、关闭时，业务已认定「未发送」，消息却稍后送达用户；审核面板看不到这条实际发出的内容；若无回执，追踪项长期残留。默认每 bot 队列 100 条 × 0.5 秒间隔，排队超过 15 秒是现实场景。

**复现**：阻塞首项 → 第二条入队后取消调用方 → 放行：第二条仍发出（1 条），归档任务 0，`pending_sent=1`、`pending_responses=1`。

**修复方案**：
- 队列项增加状态 `queued → dispatching → dispatched`；worker 在取出和限速等待之后、真正发送之前检查取消标记，已取消则跳过并 `task_done()`。
- 已进入发送阶段的消息不可撤回，归档改由传输层自己的受监管任务负责，不依赖调用方是否还在等待。
- `_send_tracked` 显式处理 `CancelledError`：未发送则清理追踪，已发送则交给归档任务，然后重新抛出。
- **不要**简单加 `shield` 强制发送所有过期消息。

**验收**：在入队、排队、限速睡眠、发送中、等待回执五个时点取消；未发送项永不迟发且无残留，已发送项恰好归档一次。

### P1-3 回复过滤器在朗读标签内放行思考/工具块；纯英文比较式被误删

**位置**：[reply_filter.py:239–257](<../mohobot/utils/reply_filter.py#L239-L257>) voice 状态下非朗读标签一律原样输出，绕过 DROP 策略；[reply_filter.py:56–58](<../mohobot/utils/reply_filter.py#L56-L58>) 尖括号属性部分接受任意 ASCII。

**用户影响**：模型把 `<think>` 或 `<tool_call>` 包进 `<tts>` 时，内部推理和工具参数同时出现在文字和语音里，并写入记忆。`a < b && c > d` 这类代码/英文比较被改成 `a  d`。

**复现**：`<tts>可见<think>INTERNAL_REASON</think><tool_call>TOOL_SECRET</tool_call>正文</tts>` → 显示文本和朗读文本都包含两个内部块，整串与逐字符流式结果一致；`a < b && c > d` → `a  d`。

**修复方案**：
- DROP 优先级高于 voice：voice 内遇到 drop 标签时压栈进入 drop，闭合后回到 voice；drop 内容不进显示也不进朗读。
- 收紧尖括号标签语法：标签名后必须是空白+属性或直接 `>`，属性值须带引号；对歧义 ASCII 比较式保守原样输出。
- 保留现有多段合并、别名、游离闭标签、超长畸形救援策略。

**验收**：各朗读别名与括号形态 × think/tool/format 嵌套 × 闭合/未闭合；所有两段切分点及逐字符结果一致；纯 ASCII 比较、泛型、代码片段原样保留。

### P1-4 关闭流式时，第二轮工具调用被静默丢弃

**位置**：[llm_service.py:263–309](<../mohobot/llm_service.py#L263-L309>) 只执行一轮工具，第二次请求仍提供工具，但只读 `content`，忽略新的 `tool_calls`；流式路径 [415–539](<../mohobot/llm_service.py#L415-L539>) 有多轮循环。

**用户影响**：`reply.stream=false` 时，「搜索 → 查详情」「换关键词再搜」等链式工具场景里，用户收到空回复或半截回答，第二个工具从未执行。

**复现**：预设 lookup → fetch → answer 三次响应：实际只请求 2 次、只执行 lookup、回复为空。

**修复方案**：抽出流式/非流式共用的有界工具循环（上限沿用 `max_tool_rounds=4`，最后一轮去掉 tools 强制出正文）；每轮的 client、模型、温度、`max_tokens`、人设固定为本轮捕获值。

**验收**：两种模式跑同一组多轮/多工具/空答重试/达上限/副作用计次用例，结果一致。

### P1-5 所有人可用的 `/meme list` 泄漏其他群的「仅本群」表情

**位置**：[image_mgmt_command.py:85–130](<../plugins/meme_stealer/meme_stealer_core/core/commands/image_mgmt_command.py#L85-L130>) 列表只按分类分页，不检查作用域；渲染器读取真实图片生成缩略图发回当前会话。

**用户影响**：管理员把群 A 的表情设为 local（仅群 A 可用）后，群 B 任何成员执行 `/meme list` 即可看到 A 的图片缩略图和描述。搜索/发送路径有作用域检查，列表是遗漏的旁路。

**复现**：local、来源 `group:A` 的条目，在 `group:B` 非管理员事件中执行真实 `list_images` → 渲染列表包含该条目及描述「ONLY_FOR_A」。

**修复方案**：在数据库查询层加入作用域条件（`public` 或 `origin_target` 等于当前会话），再分页和计数；fallback 分支同样处理。管理员需要看全部时，由入口显式传入授权，不能靠事件为空绕过。

**验收**：群 A/B、私聊、多 bot、分类、翻页、图片与纯文本两种输出；非授权会话看不到受限图片、描述和计数。

### P1-6 表情包 `steal_meme` 工具可处理当前消息以外的本机图片或任意地址

**位置**：[meme_steal_tool.py:175–181、221–222](<../plugins/meme_stealer/meme_stealer_core/core/tools/meme_steal_tool.py#L175-L222>) 对模型传入的 http/https/file 引用直接信任，匹配失败还原样返回；[62–85](<../plugins/meme_stealer/meme_stealer_core/core/tools/meme_steal_tool.py#L62-L85>) 读取或下载后交给视觉模型并入库。

**用户影响**：开启偷图后，普通聊天中模型若输出一个本机绝对路径或内网地址，进程可读的图片会被上传到视觉服务并进入公共图库；下载链没有私网校验和大小上限（外部来源导入有完善防护，但不覆盖此路径）。这是能力边界问题，不等于任何用户都能稳定诱导。

**复现**：消息中没有任何图片，传入临时目录外的自制 PNG 绝对路径 → 真实工具流程把该文件交给处理函数（假视觉模型，未上传）；内网 URL 被解析器原样接受。

**修复方案**：工具参数改为「当前消息/引用消息中的图片序号」，候选只来自事件和可信的 `get_msg/get_image`；删除任意 URL/路径兜底。如需保留远程下载，复用外部来源模块的地址校验和有界流式下载。

**验收**：事件外路径、内网/公网 URL 在读取前被拒；当前图、引用图、仅 file 的 NapCat 图、inline、商城表情继续可用。

### P1-7 关系插件「被踢自动拉黑」从未生效

**位置**：[notice/handle.py:42–45](<../plugins/relationship/relationship_core/notice/handle.py#L42-L45>) 调用异步方法 `add_black_group/add_block_user` 时漏写 `await`。

**用户影响**：默认开启的「被踢后拉黑群和操作者」只回复「已拉黑」，名单实际不变，bot 可被同一群反复拉入踢出。

**复现**：模拟 `kick_me` 通知 → 黑名单群/用户均为空，产生 2 个 `coroutine was never awaited` 警告。

**修复方案**：补 `await`。**注意**：用户目标当前传的是 `notice.user_id`，在 kick_me 中就是 bot 自己；只补 `await` 会把 bot 拉黑自己，必须同时改为 `notice.operator_id`。

**验收**：kick_me 后黑名单含群号和操作者 QQ，不含 bot 自身；无未等待协程警告。

### P1-8 QQ 空间「每条说说回复上限」只在循环外检查一次

**位置**：[qzone/main.py:626–661](<../plugins/qzone/main.py#L626-L661>) 上限检查在逐评论循环之前，循环内回复后计数但不再检查。

**用户影响**：一次轮询看到同一条说说下多条新评论时，全部自动回复，超出上限，每条都消耗一次 LLM 调用。

**复现**：上限 1、一次轮询 3 条新评论，调用真实 `_monitor_own_comments` → 回复 3 条、计数 3。

**修复方案**：在内层循环每次回复前重新检查上限，达到后跳出该说说；超出部分标记已读或保留待下轮，需明确选择一种。

**验收**：上限 1/2/0（不限）× 单轮多条评论 × 跨轮累计。

### P1-9 旧数据库自动改名时丢失 WAL 中已提交的数据

**位置**：[database_manager.py:25–35](<../mohobot/db/database_manager.py#L25-L35>) 只 `os.rename` 主文件；[sql_database.py:119–142](<../mohobot/db/sql_database.py#L119-L142>) 固定使用 WAL。

**用户影响**：从旧版 `luotianyi.db` 升级到 `mohobot.db`，若旧进程异常退出、最近提交仍在 `luotianyi.db-wal`，改名后新库读不到这些记录，启动却完全正常。影响 SQL 对话档案，不影响 contexts 和 history；旧 WAL 仍在磁盘上，可人工恢复。

**复现**：子进程提交数据后 `os._exit` 留下 WAL → 按原名读取能看到；调用真实 `DatabaseManager` 改名后，表不存在。

**修复方案**：改为 SQLite backup API 复制到临时目标 → `quick_check` 与行数校验 → 原子替换；旧文件三件套完整保留作为备份；失败时停止启动并报错，不得静默新建空库。

**验收**：正常库、WAL 未合并、空 WAL、两库同时存在、复制中断后重启。

## 待验证风险（调用链确定，自然触发概率未证实）

1. **引用缓存跨 bot 共享**：[message_handler.py:779–830](<../mohobot/message_handler.py#L779-L830>) 类级字典只以 message_id 为键。若两个账号出现相同 message_id，B 会读到 A 的私聊内容。需确认 NapCat 等实现的 ID 是否全局唯一；修复成本低（键加入 bot 与会话），建议直接修。
2. **TTS 超时热更新不作用于已有连接**：已复现配置改为 5 秒后实际读超时仍为 60 秒；影响有限，可在 `sync_config` 中关闭旧客户端。
3. **CQ 字符串消息的 @ 与引用不被识别**：群门控与引用解析只处理数组格式；仅影响上报字符串格式的协议端配置。

## 已核查但不列为缺陷

- A/B 评估在图片投递未知时降级为纯文本、重启恢复、投票归属与幂等、切换人设校验均有实现和测试。
- 外部来源 HTTP/GitHub 的地址校验、重定向检查、ZIP 防护和并发上限完善。
- 面板 Bearer 认证、备份 ZIP 路径防护、systemd 专用用户均有效；`compare_digest(token, token)` 是无意义代码但不构成认证绕过。
- 面板备份范围选择处 [index.html:2565](<../mohobot/web_panel/static/index.html#L2565>) bot 昵称未转义，可被管理员写入的昵称注入脚本；仅已登录管理员可写入，影响有限，建议顺手改为转义输出。

## 测试覆盖缺口

1. 根 runner 不运行 unittest 类和 `main()`：[test_ban_pipeline.py](<../tests/test_ban_pipeline.py>)（14 例）与 [test_plugin_reload.py](<../tests/test_plugin_reload.py>) 记为 PASS 但零执行。
2. [test_qzone.py](<../tests/test_qzone.py#L234-L301>) 4 个同步测试返回协程，runner 不等待，产生 `never awaited` 警告。
3. [test_new_features_2.py](<../tests/test_new_features_2.py#L290-L334>) 用量测试的内层断言从未执行。
4. 插件 `snitch.py` 在每次加载全部插件时报「duplicate LLM tool」，测试日志中反复出现，需确认是否影响热重载。

**建议**：runner 改为同时收集 unittest 类、等待返回的协程、零用例文件标为失败；或整体迁移到 pytest（插件已在使用）。
