# REQ-6 新闻动态注入与主动话题功能设计方案

> 对应需求: REQ-6 (新闻动态注入与主动话题功能)

---

## 1. 业务目标与需求背景

为了增强 Bot 的主动互动意愿和对话时效性，在与用户的日常聊天及主动发说说（Qzone Lite）时，引入近期的官方资讯与行业热点。

**核心功能诉求**：
1. **多途径新闻采集与提取**：
   - 外部爬取/订阅：B站官方号动态/视频、知名 UP 主相关更新；
   - 内部交互提取：由 LLM 在聊天互动中自主感知、提取可信的热点新闻片段。
2. **入库审核机制**：
   - 为避免不实言论、恶意伪造或负面敏感信息直接污染 Bot 的知识库，**所有新增内容均须经管理员审核**后方可正式入库生效。
3. **两类消费场景**：
   - **主动注入（Prompt 增强）**：在生成主动说说或日常群聊开场白时，按权重注入最新且相关的新闻话题素材；
   - **按需调取（Function Call / Tool）**：向 LLM 注册查询工具（如 `get_recent_news`），当用户提问“最近有什么新歌/新动态吗”时，Bot 可主动调取已过审新闻。

---

## 2. 系统架构设计

```
[B站动态/视频爬虫] ────┐
                       ├─▶ [统一归一化为 NewsItem] ─▶ [数据库: 待审核表 (pending)]
[LLM 聊天中提取] ──────┘                                    │
                                                            │ (WebUI 管理员审核)
                                                            ▼
                                             ┌──────────────┴──────────────┐
                                             │                             │
                                             ▼                             ▼
                                     [审核通过 (approved)]          [驳回/废弃 (rejected)]
                                             │
                       ┌─────────────────────┴─────────────────────┐
                       │                                           │
                       ▼                                           ▼
          [场景 A: 系统提示词动态注入]               [场景 B: LLM Tool: get_recent_news]
          (用于主动聊天 / 发说说话题池)               (用户对话中主动按需召回)
```

---

## 3. 详细设计规范

### 3.1 核心数据结构 (`mohobot/models/news.py` 或插件内部模型)
```python
@dataclass
class NewsItem:
    id: str                        # UUID 或 内容 hash
    source: str                    # "bilibili_official" | "bilibili_up" | "chat_extracted"
    title: str                     # 新闻标题 / 核心摘要
    content: str                   # 详情正文 / 动态内容
    url: str                       # 来源链接 (如 B站动态链接)
    author_name: str               # 来源发布人 (如 "洛天依_官号", "某知名UP")
    author_id: str                 # 来源标识 (如 B站 UID)
    tags: list[str]                # 话题标签 (如 ["新歌发布", "线上演唱会"])
    status: str                    # "pending" | "approved" | "rejected" | "expired"
    published_at: float            # 外部发布时间戳
    created_at: float              # 抓取/提取入库时间戳
    reviewed_at: float | None      # 审核通过时间戳
    reviewed_by: str | None        # 审核人
    expires_at: float | None       # 过期时间 (新闻具备时效性，默认例如 7~14 天过期)
```

### 3.2 采集模块实现建议
1. **B站动态监控**：
   - 可配置关注的 UID 列表（如官方号、特定音乐社团）；
   - 使用轻量 HTTP 接口或抓取轮询，提取动态文本、头图与发布时间；
   - 带有反爬冷却与本地缓存，轮询间隔可配（建议 15~30 分钟一次）。
2. **聊天自提取机制**：
   - 类似于情感系统记忆提炼，在会话总结阶段或命中特定关键词时，通过低开销小模型抽取结构化热点新闻，提交入待审队列。

### 3.3 审核工作流 (Review Flow)
- 仿照现有 `review/` 或在 WebPanel 中增设“新闻资讯审核”板块；
- 支持在 Web 面板查看待审列表、原文链接、来源标识；
- 提供一键“批准”、“驳回”以及“快速编辑标题/标签”。

### 3.4 消费与注入策略
1. **主动说说集成 (`plugins/qzone`)**：
   - 扩展现有 `_pick_topic`，在从情感长期记忆挑选话题的基础上，增加可选的新闻话题池；
   - 若命中已过审的新闻条目，以其标题和要点作为创作灵感。
2. **LLM 工具注册 (`mohobot/services/llm_tools.py`)**：
   - 工具名：`get_recent_news`
   - 参数：`keywords`（可选关键词）、`limit`（返回数量，默认 3 条）
   - 实现：查询状态为 `approved` 且尚未过期的条目，返回格式化标题、发布者与摘要。

## 4. 实施阶段规划

1. **第一阶段：数据存储与管理接口**
   - 建立 SQLite 数据表与迁移逻辑；
   - 编写 WebUI 审核与展示端点。
2. **第二阶段：LLM Tool 与主动提示词接入**
   - 实现 `get_recent_news` 工具；
   - 在主动发说说插件中打通新闻话题池通道。
3. **第三阶段：外部采集源（B站等）与聊天自动提取接入**
   - 编写稳健的离线与定时拉取器，完善异常降级与速率保护。
